Flary OSS is self-hosted. It does not require Flary Cloud or Better Auth. Your
Worker is the public host. Flary supplies the typed function API, Code Mode,
durable run contracts, tool policy, and provider adapters.

## Minimal architecture

~~~text
Your Worker
  ├─ authenticate request
  ├─ resolve tenant, user, grants, and provider credential
  ├─ define functions with flary() and app.fn()
  └─ export app.serve({ ...functions })

Flary
  ├─ Flue Durable Object: canonical transcript and execution stream
  ├─ Durable Object SQLite: run admission, replay projection, idempotency, and results
  ├─ R2: large files and optional immutable history fallback
  └─ optional Dynamic Workers, Sandbox, Artifacts, and Turbopuffer
~~~

Use one thread Durable Object per conversation or coding thread. Do not route
all tenant traffic through one object. Use a separate workspace object for a
project branch when the agent edits files.

## Create the Worker

```bash
npx flary@next create my-agent
cd my-agent
npm install
npm run dev
```

For an existing Worker:

```bash
npm install --save-exact flary@next
npx flary init
```

The generated starter uses `flary()`, `app.fn()`, `app.tools()`, and
`app.serve()`. The Vite build generates the Flue agent/workflow entry, the
Flary run Durable Object, bindings, and SQLite migrations. Apply the generated
Wrangler configuration before a production deploy.

## Bind resources

Add the generated Durable Object bindings to the host Worker. The exact
Durable Object classes and binding names come from the pinned Flue build.

~~~jsonc
{
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "my-agent",
      "database_id": "replace-with-your-database-id"
    }
  ],
  "r2_buckets": [
    {
      "binding": "WORKSPACE_BLOBS",
      "bucket_name": "my-agent-blobs"
    }
  ],
  "worker_loaders": [
    { "binding": "LOADER" }
  ]
}
~~~

The D1 block is optional and is used only by the advanced low-level run
adapter. The generated function-first Wrangler configuration uses Durable
Object SQLite for run state.

The Vite build includes `FlaryRuntime`, the Flue registry, and one
agent/workflow class for each function. Apply the generated Durable Object
SQLite migration through your normal Wrangler deployment process:

~~~ts
// No handwritten run-store migration is required. Use the generated
// `flary.wrangler.json` or `.flue-vite.wrangler.jsonc` file.
~~~

R2 is optional for a basic chat function. Production needs it for workspace
files larger than 1,500,000 bytes or for the immutable history fallback.

## Define a durable function

```ts
// src/flary.ts
import { flary, z } from "flary";

export const app = flary<Env>({
  name: "support",
  model: "anthropic/claude-sonnet-4-5",
  bindings: z.object({
    ANTHROPIC_API_KEY: z.string().min(1),
    LOADER: z.unknown(),
    APP_ENV: z.string(),
  }),
  auth: async ({ request, bindings }) => {
    const caller = await authenticateProductRequest(request, bindings);
    return {
      tenantId: caller.tenantId,
      userId: caller.userId,
      applicationId: "my-product",
      projectId: caller.projectId,
      roles: caller.roles,
      scopes: caller.scopes,
    };
  },
});
```

```ts
// src/support.ts
import { z } from "flary";
import { app } from "./flary";

export const support = app.fn({
  input: z.object({ message: z.string().min(1) }),
  output: z.object({ answer: z.string() }),
  mode: "ask",
  prompt: ({ message }) =>
    `Answer this support question from approved product facts:\n${message}`,
});
```

```ts
// src/index.ts
import { app } from "./flary";
import { support } from "./support";

export default app.serve({ support });
```

`app.serve()` reads bindings from the incoming Worker request. `auth` returns
trusted identity and tenant context; those values never come from the public
JSON body. For functions with tools, register them with `app.tools()` and
keep credentials in `run` closures or trusted connection resolvers.

## Add Flue-backed execution

The function-first host is generated by `flary/vite`. It attaches the Flary
Runtime Durable Object to the authored `flary()` application and supplies the
Flue agent/workflow bindings. Do not add a second run service to the starter.

For a custom low-level host, the function definition can still connect to a
manually assembled run service. The D1 repository example remains available
for that advanced path:

```ts
import { D1FlaryRunRepository } from "flary/cloudflare";
import { createFlueAgentGateway, createFlueRunService } from "flary/flue";
import { flary, z } from "flary";

export const app = flary<Env>({
  bindings: z.object({ DB: z.any(), SELF: z.any() }),
  runService: ({ bindings, waitUntil }) =>
    createFlueRunService({
      repository: new D1FlaryRunRepository(bindings.DB),
      gateway: createFlueAgentGateway({
        baseUrl: "https://internal.flue",
        fetch: bindings.SELF.fetch.bind(bindings.SELF),
      }),
      schedule: (work) => waitUntil?.(work),
    }),
});
```

Use the generated host for work that must survive a browser disconnect or
Worker eviction. The direct function call and durable function route use the
same Zod schemas and function name. The generated Runtime Durable Object uses
SQLite by default; D1 is not required for the function-first path.

## Deploy

```bash
npm run build
wrangler deploy
```

If the custom low-level D1 adapter is enabled, create the D1 database and
apply its migration as part of the host deployment.

Use the host's migration directory in a real application. Do not apply
production migrations from a developer laptop without the deployment review
used by the rest of your application.

## Self-hosting checklist

- Pin Flary, Flue, Pi, and Cloudflare package versions.
- Run Flary's clean npm installation test in CI.
- Authenticate every public route before resolving trusted context.
- Store provider credentials in an encrypted vault or the host's secret
  system. Never place them in prompts or model-visible tool arguments.
- Use tenant-scoped R2 keys and authorize every object operation.
- Set a mode and tool allowlist for every function revision.
- Give writes idempotency keys and require approval for risky operations.
- Test disconnect, replay, restart, cancellation, and credential rotation.
