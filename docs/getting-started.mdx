Flary has three entry points:

1. One-off function: define a typed function and call a provider from any
   TypeScript application.
2. Self-hosted runtime: run durable threads in your Cloudflare Worker.
3. Product integration: keep your authentication, UI, billing, and connections
   while Flary supplies the agent runtime.

Start with the smallest layer that matches the job. The function API is the
default authoring surface. You can call a function directly, start it as a
durable run, or expose the same function through HTTP.

Before you build a persistent agent, read [Sessions, workspaces, and
storage](/docs/sessions-and-workspaces/). It explains why messages, files,
checkpoints, and indexes use different durable stores.

## Install

Flary 0.7 is the current function-first release. The normal install command
resolves the current `latest` npm tag and records it in the application lockfile.

```bash
npm install flary
```

Add a prompt example to an existing project:

```bash
npx flary init
```

Create a small Cloudflare Worker starter:

```bash
npx flary create my-agent
cd my-agent
npm install
npm run dev
```

The starter uses the function API. Its Vite build generates the Flue runtime,
the Flary run and Thread Control Durable Objects, bindings, and SQLite
lifecycle configuration. Apply the generated Wrangler configuration before a production deploy. Use [One-off
agent](/docs/one-off-agent/) for a small call or
[Self-hosting](/docs/self-hosting/) for a durable deployment.

Before a production deploy, replace the starter's loopback-only placeholder
authentication. It rejects all deployed requests until the application
returns a trusted tenant identity. Then set the provider and internal runtime
secrets:

```bash
npx wrangler secret put OPENAI_API_KEY
openssl rand -hex 32 | npx wrangler secret put FLARY_INTERNAL_TOKEN
```

Wrangler prompts for `OPENAI_API_KEY`. The second command generates a random
64-character value and sends it directly to Wrangler.

## Define a function

Create one typed function. A `run` function is deterministic application code.
A `prompt` function sends the generated prompt to the configured model and
validates the result with its output schema.

```ts
// src/flary.ts
import { flary, z } from "flary";

export const app = flary({
  name: "support",
  model: "openai/gpt-5",
  bindings: z.object({
    OPENAI_API_KEY: z.string().min(1),
  }),
});
```

```ts
// src/support.ts
import { z } from "flary";
import { app } from "./flary";

export const support = app.fn({
  input: z.object({ question: z.string().min(1) }),
  output: z.object({ answer: z.string() }),
  prompt: ({ question }) =>
    `Answer this support question clearly and briefly:\n\n${question}`,
});
```

Call it from server code:

```ts
const result = await support({ question: "How do I change my plan?" });
console.log(result.answer);
```

## Expose functions over HTTP

Register functions once. Flary creates the health, direct-call, durable-run,
status, cancellation, approval, and user-input routes.

```ts
// src/index.ts
import { app } from "./flary";
import { support } from "./support";

export default app.serve({ support });
```

The direct route is `POST /functions/support`. A durable invocation starts at
`POST /functions/support/runs`; the returned run ID can be polled after a
disconnect. The function client exposes this as `run.stream()`. See
[Durable threads](/docs/durable-threads/) for the low-level SSE route.

## TypeScript, HTTP, and serverless boundaries

You do not have to write `app.get()` or `app.post()` routes for Flary. There
are three separate ways to use the package:

| API | HTTP server required | Cloudflare durable resources required |
| --- | --- | --- |
| Call `app.fn()` directly | No | No |
| Serve direct functions with `app.serve()` | Yes | No |
| Use `app.agent()` or durable `.start()` | Yes | Yes, through the generated Cloudflare host |

`app.serve()` returns a Hono application and registers all Flary routes. It
can be the Worker export:

```ts
export default app.serve(functions, { prefix: "/api/flary" });
```

It can also be mounted in an existing Hono application:

```ts
import { Hono } from "hono";

const server = new Hono();
server.route("/api/flary", app.serve(functions));

server.get("/api/health", (context) => context.json({ ok: true }));
export default server;
```

The authoring API is normal TypeScript. The complete persistent-agent runtime
is Cloudflare-native today because it uses Durable Objects, D1, Queues, and R2
for restart-safe state. Use Wrangler locally to emulate those resources.

## Define a persistent agent

Use `app.agent()` when several messages must share one durable session:

```ts
export const supportAgent = app.agent({
  name: "support-agent",
  model: "anthropic/claude-sonnet",
  models: {
    allow: ["anthropic/claude-sonnet", "openai/gpt-5.6-sol"],
    switching: "user",
    fallback: "none",
  },
  instructions: "Resolve the support issue and keep the customer informed.",
  tools,
});

export const functions = { support, supportAgent };
export default app.serve(functions);
```

The client stores only the thread ID and stream cursor:

```ts
const thread = await api.supportAgent.threads.create({
  workspace: {
    organizationId: "acme",
    appId: "support-agent",
    projectId: "support",
    workspaceId: "ticket_42",
    branch: "main",
  },
  mode: "ask",
});

await thread.send({ message: "Investigate ticket 42." });
```

Open the same thread ID from a web UI, Telegram bot, Discord bot, or support
worker. See [Telegram, Discord, and custom UIs](/docs/channels-and-webhooks/).

## Keep prompts in Git when you need Markdown

Create `prompts/support/answer.prompt.md`:

```md
---
model: inherit
thinking: medium
tools:
  - docs.search

input:
  customer.name: string
  question: string
---

Answer {{customer.name}} with a concise, sourced response:

{{question}}
```

Compile a prompt file with the low-level compiler:

```ts
import { readFile } from "node:fs/promises";
import { compilePrompt } from "flary/prompts";

const path = "prompts/support/answer.prompt.md";
const prompt = await compilePrompt(
  {
    path,
    content: await readFile(path, "utf8"),
  },
  {
    callerModel: "openai/gpt-5.6",
    values: {
      customer: { name: "Ada" },
      question: "How do I change my plan?",
    },
  },
);
```

This path needs no Durable Object, D1 database, or R2 bucket. For new
functions, prefer a `prompt` function so its input and output schemas, tools,
HTTP route, and durable run behavior stay in one TypeScript definition.

## Add the durable runtime

A production durable thread uses:

- A Cloudflare Worker as the host.
- One Flue Durable Object for each thread.
- The generated Flary Runtime Durable Object with SQLite for trusted run
  bindings, replay events, idempotency, and materialized results.
- D1 only when an application chooses the advanced low-level run adapter.
- R2 only when the application stores large workspace files or uses the R2
  history fallback.

Your host application supplies authentication, tenant mapping, provider
credentials, and product policy. Flary supplies the typed run API, durable
execution adapter, tool runtime, modes, approvals, and event stream.

Read [Self-hosting](/docs/self-hosting/) and
[Cloudflare resources](/docs/cloudflare-resources/) before deployment.

## Call a remote function

```ts
import { flary } from "flary/client";
import type { support } from "./support";

const client = flary<{ support: typeof support }>({
  baseUrl: "https://api.example.com",
  token: process.env.PRODUCT_API_TOKEN,
});

const answer = await client.support({
  question: "How do I change my plan?",
});
```

Start the same function as a durable run when you need reconnectable work:

```ts
const run = await client.support.start(
  { question: "How do I change my plan?" },
  { idempotencyKey: "ticket_42:turn:7" },
);

for await (const event of run.stream()) {
  console.log(event);
}
```

The function client polls the durable run status. A host that needs exact SSE
cursor control can use `createFlaryRunClient` from `flary/client` and the
lower-level [HTTP API](/docs/http-api-and-events/).

## What the host application owns

Flary is infrastructure, not a product UI. The host application owns:

- Authentication and organization membership.
- Agent and prompt revision selection.
- Provider connections, subscription ownership, and billing.
- The chat, support inbox, coding UI, or background job.
- Product-specific limits and approval presentation.

Flary owns the durable thread, trusted context checks, provider adapter,
stream replay, tool policy, approvals, workspace boundary, and normalized
events.
