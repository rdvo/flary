Flary keeps conversation state and workspace files separate. A session is not
a folder, and a workspace is not the conversation transcript.

This separation lets an agent change providers, compact its active context,
or restart after an eviction without changing the files that it created.

## The storage model

| Data | Source of truth | Purpose |
| --- | --- | --- |
| Messages, model events, and active execution | Flue thread Durable Object | Rebuild model context and continue a turn |
| Approvals, audits, goals, cursors, subagent mailboxes, and public session records | Thread Control Durable Object SQLite | Query and control a thread |
| Workspace files up to 1,500,000 bytes | Workspace Durable Object SQLite | Give the agent a durable logical file tree |
| Large workspace files | Private, tenant-scoped R2 objects | Store file content by SHA-256 digest |
| Completed-turn workspace checkpoints | Private R2 objects | Diff and restore the file tree |
| Encrypted cold session segments and canonical snapshots | Private R2 objects | Export, audit, and disaster recovery |
| Tenant thread list | D1 | List threads without scanning Durable Objects |

Flue is the only live transcript authority. Thread Control and D1 contain
projections and indexes. They do not become a second transcript.

## What happens when an agent writes a file

Assume that an agent calls the workspace tool to write `notes/answer.md`.

1. Flary checks the thread tenant, workspace binding, mode, capability, and
   approval policy.
2. The governed tool journal records the call and its idempotency identity.
3. The Workspace Durable Object writes the file. Small content stays in
   SQLite. Content larger than 1,500,000 bytes goes to R2.
4. The tool result returns to the agent and becomes part of the turn record.
5. After the turn completes, Flary creates an immutable R2 workspace
   checkpoint when the generated workspace-history binding is configured. An
   unchanged tree can reuse the previous content.

The file is now available to the parent thread and to child agents that use
the same workspace binding. A new workspace branch gets a different logical
file tree.

The file is not copied into a local server folder. It is also not injected in
full into every later model request. The agent uses lazy `list`, `glob`,
`grep`, and `read` tools to load only the files that it needs.

### The durability rule

A write is durable when it goes through the Flary workspace tools. A file
created only inside a Linux Sandbox belongs to that Sandbox filesystem until
the application imports or synchronizes it. Flary 0.7 does not automatically
copy every Sandbox file into the Workspace Durable Object.

Attachments and large tool results also use separate R2 references. They do
not become workspace files unless the application or agent saves them there.

## Session history is not the workspace

A session stores user messages, assistant messages, tool calls and results,
provider and model pins, compaction lineage, rollback markers, approvals,
usage, and subagent activity.

The recent public projection stays in Thread Control SQLite. When it exceeds
the 10,000-record hot window, Flary compresses and encrypts older segments and
seals them in R2. Flary also captures encrypted canonical Flue snapshots when
the archive binding is configured.

Normal history and audit APIs return redacted records. Trusted export and
restore paths can use the encrypted canonical data. Provider credentials and
plaintext hidden reasoning do not enter the public ledger.

## Reopen the same thread

Store the authenticated `threadId` and the last event cursor in the client.
The client does not send the full conversation again:

```ts
const thread = await api.coder.threads.open({
  organizationId: "acme",
  threadId: savedThreadId,
});

for await (const event of thread.stream({ after: savedCursor })) {
  render(event);
}

await thread.send({ message: "Continue from the current workspace." });
```

The same thread can be opened from a web application, support system,
Telegram bot, or Discord bot. Tenant authorization is checked on every
operation.

## Current Codex-parity boundary

Flary 0.7 has durable threads, provider switching, resumable streams,
governed tools, approvals, shared workspaces, turn checkpoints, durable
cross-provider subagents, processes, compaction, rollback markers, schedules,
audits, and JSONL export.

It is not yet a complete Codex replacement. The main remaining runtime work
is:

1. Restore an exported canonical session directly into live Flue context.
2. Fork a thread with the exact model-visible canonical history, not only its
   control-ledger projection.
3. Enforce root-wide tool-call limits transactionally across all child
   threads.
4. Mount or synchronize the durable workspace with the Linux Sandbox so a
   shell command and a workspace tool always see the same checked-out tree.
5. Add a first-party coding handoff that can create a branch, push it, and
   open a pull request without application-specific MCP or OpenAPI wiring.
6. Complete live eviction and provider-recovery tests for deployed OpenAI and
   Anthropic threads.

Flary targets Codex-style behavior. It does not copy the private Codex app
protocol or desktop user interface.
